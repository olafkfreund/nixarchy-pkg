# Spec: menu text follows the desktop's text size

## Design

**Decided at intent approval, carried here:** `caption` -> `title`, `body`
and `subtitle` -> `heading`, flattening accepted; the shell's `Dropdown`
needs no change because removing the multiplier resolves the mismatch; the
`OptionForm` overflow is fixed in this task; `Card.qml:211` is not.

### How the shell scales text

Verified against the installed shell, not a plugin's copy of it
(`/nix/store/...-omarchy-4.0.4/share/omarchy/shell/Commons/Style.qml:325-338`):

| token | multiplier | at base-size 12 |
| ----- | ---------- | --------------- |
| `caption` | 0.833 | 10 |
| `body` | 1.0 | 12 |
| `subtitle` | 1.083 | 13 |
| `title` | 1.167 | 14 |
| `heading` | 1.333 | 16 |

`fontBaseSize` is `[font] base-size` from `~/.config/omarchy/shell.toml`,
what `omarchy display text size 9..20` sets, and a theme may pin any token
(`fontToken`, `:290`). `Style.space()` scales by the same factor. Monitor
scale is the compositor's; QML sizes are logical pixels, so nothing here
touches it.

### The mapping

Delete `textScale` and `px()` from `Menu.qml:35-36`, `Card.qml:19,37` and
`OptionForm.qml:56-57`, delete the two `textScale:` hand-downs at
`Menu.qml:391,469`, and retoken all 31 call sites:

| today | sites | becomes | at base-size 12 |
| ----- | ----- | ------- | --------------- |
| `px(Style.font.caption)` | 21 | `Style.font.title` | 15 -> 14 |
| `px(Style.font.body)` | 9 | `Style.font.heading` | 17 -> 16 |
| `px(Style.font.subtitle)` | 1 | `Style.font.heading` | 19 -> 16 |

**Seven of the 31 are geometry, not font sizes**, and they take the same
mapping deliberately -- they exist to stay proportional to the text they
sit beside, so they must move with it:

- `Menu.qml:82` scroll step, `px(Style.font.caption) * 1.35`
- `Card.qml:25` `rowHeight`, `px(Style.font.body) * 2.2`
- `Card.qml:44` tab strip height
- `Card.qml:157` icon column width
- `Card.qml:211` summary width (the arithmetic bug is out of scope; the
  token it uses is not)
- `Card.qml:312` footer height
- `OptionForm.qml:446` scaffold box height, `px(Style.font.body) * 6`

Net effect at the default size: list rows and most labels lose 1px, body
text loses 1px, and the option path header loses 3px and stops being larger
than the body text beside it. At base-size 16 and 20 the menu is *smaller*
than today at every site, because 1.45 is a bigger step than any of these
token jumps -- so wrapping and overflow both get easier, not harder.

### The `OptionForm` overflow

`OptionForm.qml:295` is a `Column` anchored top/left/right with no `bottom`,
inside a `FocusScope` (`:29`) that sets no `clip`, inside a `BorderSurface`
that sets none either. Content taller than the card paints outside the
border, onto the scrim. It is the scope's only top-level child, so wrapping
it is contained:

```qml
Flickable {
  anchors.fill: parent
  contentHeight: column.implicitHeight
  clip: true
  Column { id: column; width: parent.width; spacing: Style.space(10); ... }
}
```

Same shape as `Menu.qml:398` (the build log) and `Card.qml:282` (the footer
message). The `Column`'s anchors become `width: parent.width`, because a
`Flickable`'s content is positioned, not anchored to it.

### The guard

A `no-text-multiplier` check in `flake.nix`, beside `no-hardcoded-colours`
(`:77-89`), in two parts:

1. **All five QML files:** no `textScale`, no `uiScale`, no `px(`. Catches
   the multiplier returning under any name.
2. **`Menu.qml`, `Card.qml`, `OptionForm.qml` only:** every `font.pixelSize:`
   right-hand side is a bare `Style.font.<token>`.

`Panel.qml` is exempt from (2) and only from (2). `Panel.qml:164` sizes the
badge's digits from the badge's own height
(`Math.round((badge.height - 2 * badge.border.width) * 0.88)`), which is a
legitimately derived size with no multiplier in it -- the badge is a circle
whose text must fit it, not a line of prose. It is still covered by (1).

## Alternatives rejected

- **`font.pointSize`.** Under Wayland the compositor applies the output
  scale and Qt's font DPI is a flat 96, so `pointSize` is `pixelSize x 4/3`
  with no added DPI awareness. It would freeze the relationship to
  `base-size`, which is the opposite of the requirement.
- **Keep 1.45, divide by `Style.fontScale`.** Yields a fixed pixel size that
  stops following the text-size setting.
- **`Style.fontPx(1.25)` / a fraction.** Scale-aware and keeps today's sizes
  exactly, but `fontPx` is an internal helper rather than a token, so it
  skips theme pins in `shell.toml` -- and the same fraction would have to be
  copied into four sibling repos.
- **A new `Style.font.menu` token upstream.** The cleanest end state and
  worth raising, but it is an omarchy change; `title` and `heading` do the
  job now.
- **Plain `caption`/`body` with no step up.** Matches the shell exactly but
  drops the deliberate larger menu, and the intent kept that.
- **Sizing the `qs.Ui` widgets instead.** With the multiplier gone there is
  nothing to size them *to* -- they already use the tokens. This was only
  ever a symptom of the multiplier.
- **Folding in `Card.qml:211`.** Its width arithmetic omits the flags
  `Repeater` and the row spacing and can go negative on a flake row, but
  that is true at every text size and was true before this change. Out of
  scope per the intent.

## Risks

- **Everything gets slightly smaller at the default size.** Intended, and
  the table above goes in the PR. The menu still sits two token steps above
  the shell's own `caption`/`body`.
- **The option path header stops standing out.** Accepted at intent
  approval. `OptionForm.qml:305` is the only `subtitle` site; if it reads
  badly on razer, the fallback is `display` (24px), and that is a one-line
  change recorded here rather than a re-plan.
- **A theme that pins `title` or `heading`** changes the menu with it. That
  is the point -- it follows the theme -- but a theme pinning `heading` very
  large could make the menu larger than 1.45 ever did.
- **The `Flickable` changes focus behaviour.** A focused control scrolled out
  of view is reachable by keyboard but invisible; Qt does not auto-scroll a
  plain `Flickable` to the focused item. Checked by tabbing through the form
  at base-size 20 on razer. If it bites, `onActiveFocusItemChanged` ->
  `contentY` is the follow-up, not part of this.
- **razer only.** Never p620.
