# Spec: CI checks the things that actually break

## Design

The intent's four questions were decided here, except aarch64, which the
approver deferred. Each decision is marked; gate 2 is where they can be
overturned.

### 1. A QML syntax gate

A `qml-syntax` check in `flake.nix`, beside `no-text-multiplier`:

```nix
qml-syntax = pkgs.runCommand "nixarchy-pkg-qml-syntax"
  { nativeBuildInputs = [ pkgs.qt6.qtdeclarative ]; }
  ''
    for f in ${./Menu.qml} ${./Panel.qml} ${./Card.qml} \
             ${./PkgModel.qml} ${./OptionForm.qml}; do
      qmllint -I "${pkgs.qt6.qtdeclarative}/lib/qt-6/qml" "$f" || exit 1
    done
    touch "$out"
  '';
```

Measured rather than assumed, because it decides whether this is possible at
all: `qmllint` exits **255** on a syntax error and **0** on a clean file,
and the 780 import warnings these files produce do **not** affect its exit
status. `qmllint` and the Qt QML module directory are in the same store
output (`.../bin/qmllint` and `.../lib/qt-6/qml`), so the check needs
nothing else.

**Decision (Q4): pass `-I`.** It does not change the gate -- the exit code
is identical either way. It drops `Failed to import` from three modules to
two, leaving only `qs.Commons` and `qs.Ui`, which come from the host shell
and cannot resolve here by design. The point is the person reading a failed
run: two unresolvable host modules is a known condition, three including
`QtQuick` looks like a broken check.

**What this deliberately does not do:** fail on warnings. Those 780 are
cascades from imports that cannot resolve outside the shell. A gate that
fires on them would be turned off within a week, and the intent forbids it.
Syntax is the contract.

### 2. The adapter suite runs on a pull request -- the half that can

**Decision (Q1): no committed fixtures. Decision (Q2): split the suite.**

`tests/adapter.sh:40` currently ends the whole run when `/etc/nixarchy` is
absent:

```bash
[ -d "$TEMPLATES" ] || { echo "skip: ... (not a nixarchy machine)"; exit 0; }
```

That guard is right about the catalogue sections and wrong about the rest.
Mapped by which sections call `fresh_config()`:

| section | needs `/etc/nixarchy` |
| ------- | --------------------- |
| `state`, `opt replace`, `writers`, `options`, `pending`, `pending across more than one file`, `a write keeps the file it wrote to` | yes |
| `flake`, `apply`, `the shape that caused it`, `failure is a value` | **no** -- they build their own `mktemp -d` fixtures, stub `nixarchy-apply` on `PATH`, or grep the source |

So the guard becomes a flag, and the catalogue sections become conditional.
Everything machine-independent runs everywhere, including CI, with **every
existing assertion unchanged**.

Why not fixtures: the templates are small (139 lines, 84 catalogue rows), so
copying them is easy -- and that is the trap. `fresh_config()` builds from
*this machine's own catalogue* on purpose. Frozen copies would make CI
assert against a catalogue nobody ships, and would quietly stop catching
drift against nixarchy's real one while looking like more coverage. A test
that is green about the wrong thing is worse than an honest skip, which is
the same reasoning already recorded at `ci.yml:17-20`.

**Cost to name:** the `flake` section's fixtures declare
`nixpkgs.url = "github:nixos/nixpkgs/nixos-unstable"`, so `nix flake lock`
fetches nixpkgs on a cold runner -- once per run, then cached. It locked
offline here only because this machine already had it. If CI time becomes a
problem the fix is to point the fixture's placeholder input at a local path
instead of GitHub, which is a change to `fresh_flake()` and out of scope
here.

### 3. `draft` and `reindex` get tested

A new section in `tests/adapter.sh`, following the PATH-stub pattern the
`apply` section already uses (`:429`):

- `draft new` and `draft undraft` forward their arguments to
  `nixarchy-pkg-new` / `nixarchy-pkg-undraft`, asserted by a stub that
  records `argv`.
- A writer that fails is surfaced as `{"ok": false}` with the writer's
  message, not swallowed.
- `draft` and `pkg` reject an unknown action with a usage error, as
  `opt replace` already asserts for itself (`:78`).
- `reindex` reports `indexStale` truthfully: with a stub `nixarchy-search`
  that does nothing, it answers `ok: false` and says the index is still
  stale -- which is the behaviour a review of #39 wrongly called a defect,
  so it is worth pinning down.

These are stub-driven and need no `/etc/nixarchy`, so they land in the
machine-independent half and run on every PR.

### 4. CI wiring

`.github/workflows/ci.yml` gains one step, `bash tests/adapter.sh`, after
`nix flake check`. The catalogue sections skip there and say so; the rest
run. `nix flake check` picks up `qml-syntax` with no workflow change.

### 5. aarch64 -- deferred, not dropped

The approver deferred it. `flake.nix:8` goes on declaring
`aarch64-linux` while CI builds only `x86_64-linux`, and
`nix flake check` goes on warning `The check omitted these incompatible
systems: aarch64-linux` on every run. Recorded here so the next reader knows
it is a known, accepted gap rather than an oversight -- the options remain
evaluate-only, build under emulation, or stop declaring the system.

## Alternatives rejected

- **Committing the three catalogue templates as fixtures.** See above: it
  buys coverage of a catalogue nobody ships and hides drift.
- **Failing `qmllint` on warnings.** 780 of them are unresolvable host
  imports. The check would be disabled within a week.
- **Adding the omarchy shell as a flake input so `qs.*` resolves.** Would
  make `qmllint` fully semantic, and would couple building this repo to the
  shell it is merely installed into. The intent forbids it.
- **Running the whole suite in CI with the catalogue guard removed.** Turns
  an honest skip into vacuous passes -- the failure mode `ci.yml:17-20`
  already warns about.
- **A separate `tests/ci.sh` holding only the portable cases.** Duplicates
  the harness and guarantees drift between two suites.

## Risks

- **Splitting the guard touches a file that currently passes.** The
  machine-independent sections are being asked to run in an environment they
  have never run in; something may fail for an environmental reason rather
  than a real one. Mitigated by running the split suite in the sandbox
  before wiring it to CI.
- **First CI run may be slow** from the nixpkgs fetch in the `flake`
  section.
- **`qmllint` version drift.** A future nixpkgs could tighten it and start
  failing on something that is not a syntax error. The check pins nothing;
  it follows `flake.lock` like everything else.
- **This adds no protection for QML *behaviour*.** #43's four defects were
  logic, not syntax, and `qml-syntax` would have caught none of them. It
  catches the class that silently ships a plugin that never draws. Saying so
  plainly matters more than the check does.
- **razer only** for anything live. Never p620.

## Verification

1. `nix flake check -L` passes with `qml-syntax` included.
2. `qml-syntax` **fails** on a scratch copy with a syntax error planted
   (`Item { {{{`), and **passes** on the tree as it stands -- the negative
   test, not committed.
3. `bash tests/adapter.sh` on razer: every section runs, all pass, and the
   count of passing assertions is not lower than before the split.
4. `bash tests/adapter.sh` in an environment without `/etc/nixarchy`: the
   catalogue sections announce they are skipped, the machine-independent
   sections run and pass, and the exit status is 0.
5. The new `draft`/`reindex` cases fail when their stub is made to fail, so
   they are assertions rather than smoke.
6. CI is green on the pull request, and its log shows the adapter suite
   running rather than skipping.
