# Spec: a real manual, on a Pages site in nixarchy's style

## Design

### 1. What the manual describes, and therefore when it is written

The intent's first open question. Recommended answer, for the approver to
overrule if they would rather:

**Write against #11 and #4 merged; the Flakes page ships with #3.**

PR #12 and PR #13 are both `MERGEABLE / CLEAN`. `feat/3-flake-input` is
thirteen commits, unpushed, and conflicts with #11 -- so blocking the
manual on it blocks it on a rebase that has not happened. Writing against
`main` instead documents a tab called `Packages` that #11 renames, which
is wrong the day #12 merges.

So: merge #12 and #13, branch the manual from that, and add
`manual/flakes.md` in #3's own PR, where the feature and its page land
together. The sidebar check below is meant to fail loudly if that page is
forgotten -- see the plan, where that claim turned out to need a second
direction of checking before it was true.

### 2. The site

`docs/`, arranged exactly as nixarchy's is, because a contributor who
knows one should be able to edit the other:

    docs/
      _config.yml          title, baseurl, the nav in reading order
      _layouts/home.html   the landing page
      _layouts/manual.html masthead, sidebar, content
      _includes/logo.html  the wordmark
      assets/style.css     the whole of the styling
      assets/manual.js     the sidebar filter, and `/` to focus it
      llms.txt             the same index, for a reader that is a model
      manual/*.md          one page per surface
      img/*.png            the screenshots

No theme gem, so what builds on Pages is what is in the directory.

`style.css` and `manual.js` are **copied** from nixarchy rather than
referenced -- a stylesheet cannot be shared across repositories without a
build step, and the intent forbids one. That forks them, and the fork is
stated in a comment at the top of each file naming where it came from, so
the next person knows a fix may need making twice rather than discovering
it.

The wordmark is this project's own, not nixarchy's. `assets/package.svg`
is the parcel mark from #10 and is what the plugin already uses in the
bar. Borrowing nixarchy's block-drawing art would put nixarchy's name on
a different project's manual.

### 3. The pages

One per surface, each titled as a thing a person does rather than a
component name. In reading order, which is the order `_config.yml` states:

| Page | The story it tells |
| --- | --- |
| `index` | What this is, and which of the two installs you have |
| `getting-started` | Flake-adopter first, then ISO. Ends with one package installed |
| `the-menu` | The card: tabs, list, the message line, the footer, the queue |
| `the-bar` | The badge, why a queued change is otherwise invisible |
| `apps-and-services` | The curated catalogue, `SPACE`, `■ □ ≡`, filtering |
| `packages` | Searching nixpkgs, adding, `unfree`/`broken`, the other channel |
| `options` | Every NixOS option, the five widgets, and why some get a scaffold |
| `drafts` | Derivations for software nixpkgs does not carry |
| `flakes` | Declaring an input (**ships with #3**, not before) |
| `applying` | `a`, `SHIFT+A`, the log, and why detaching does not stop a build |
| `from-a-terminal` | The adapter CLI |
| `how-it-works` | Selection files, markers, the writers, what is not managed |
| `troubleshooting` | Stale index, refusals, nothing happened, it is still installed |

`index` links every page, the sidebar lists every page, and `llms.txt`
lists every page. Three hand-maintained indexes is what nixarchy has, and
CI checks all three (below) because all three had drifted there.

### 4. The voice, and what goes in it

The manual answers "what do I do, and what happens then". It is not a
feature list and it is not a second key table -- `?` is generated from
`bin/nixarchy-pkg-keys` and is on screen when the question is asked; the
manual says what a key is *for*.

The measurements this project has already had to make are the content,
because they are what a person trips over:

- a selection is not the machine: a package declared elsewhere in your
  own configuration is neither listed nor managed here (#11)
- a stale index reports every package as free, so the flags are absent
  rather than negative
- the two channels share no store paths, so the other channel costs a
  whole closure -- `nixarchy-doctor` measures vlc at 1.5 GB
- `nix flake show` enumerates `nixosModules` and cannot see inside
  `homeManagerModules`
- an untouched option field writes nothing, on purpose

Each such claim is checkable against the code or a command that was run.

### 5. The screenshots

`assets/showcase/` already has eleven, and their README is close to the
voice this manual wants. They are **not** reusable as they stand: they
are dated before #11, so four of them show a tab named `Packages` that no
longer exists, and none show `SHIFT+RETURN` or Flakes.

They are re-captured against the merged tree, by the same method their
README describes -- the real plugin, driven from the keyboard, with the
selection files checksummed before and after to prove nothing was
installed. `assets/showcase/` remains the source; `docs/img/` is what the
site serves.

Nothing from a real machine's package list, no home-directory paths in
frame.

### 6. CI

A workflow, `.github/workflows/pages.yml`, doing three things:

1. **Reachability.** Every `docs/manual/*.md` appears in the
   `_config.yml` nav, in `llms.txt`, and is linked from
   `manual/index.md`. Lifted from nixarchy's build.yml:714, whose comment
   records why -- four pages had drifted out of the nav, and the welcome
   table had drifted to 24 of 26, leaving "two of the features most worth
   showing a new reader" unreachable from the page a reader lands on.
   Membership only, not order: where a page belongs in a reading order is
   a judgement, whether it is reachable at all is not.
2. **Build**, with `actions/jekyll-build-pages`, so a broken Liquid tag
   or a missing layout fails the PR rather than the deployment.
3. **Deploy**, with `actions/deploy-pages`, on `main` only.

nixarchy lets Pages build its directory natively and has no deploy
workflow. This does it explicitly because it was asked for, and because
the reachability check has to run on pull requests, where a native Pages
build does not.

Turning Pages on, and setting its source to GitHub Actions, is a
repository setting. This task cannot do it; the plan says so and says
exactly what to click.

### 7. The README shrinks

It becomes what a README is for -- what this is, what it is not, how to
install it, and a link to the manual. The prose that is really manual
prose moves to the page that owns it. The "What it is not" section stays:
it is the boundary statement, and it belongs where somebody evaluating
the project will see it.

### 8. nixarchy's manual

`manual/other-packages.md` there describes the same writers from the CLI
side. The two should point at each other. This task can only do its half:
the pages link to nixarchy's manual where a topic is theirs. The other
half is an issue on the other repository, opened but not merged from
here.

## Alternatives rejected

**Lengthen the README.** Produces a worse README and still no manual. The
questions in the intent are not answerable in a project README's shape.

**A theme gem.** Would look approximately like nixarchy's and behave
differently, and what builds on Pages would stop being what is in the
directory.

**Reference nixarchy's stylesheet instead of copying it.** Cross-repo
asset sharing needs a build step, which the intent forbids.

**Reuse the existing screenshots.** They predate #11; four show a tab
name that no longer exists.

**Generate the key table into the manual.** A second surface to keep in
step with `bin/nixarchy-pkg-keys`, when the first is already on screen
at the moment of asking.

**Write the manual now against `main`.** Wrong the day #12 merges.

**Block everything on #3.** Blocks the manual on an unpushed branch that
conflicts with #11.

## Risks

- **The manual dates.** Every page describes a surface that can change.
  Mitigated by the reachability check, which catches a missing page but
  not a stale sentence; nothing catches a stale sentence but review.
  Stated rather than pretended away.
- **The copied stylesheet forks.** A fix to nixarchy's CSS will not reach
  here. Accepted, with the provenance in a comment.
- **Re-capturing screenshots needs a real desktop** and the panel built
  from the merged tree. It cannot be done in CI, and a shot taken on a
  machine with a full selection would publish that machine's package
  list. The plan pins the method.
- **Documenting the adapter makes it an interface.** Settled at gate 1
  and taken deliberately: once `state` and `flake show` output is in the
  manual, its shape cannot change quietly. The page says which fields are
  stable and which are the panel's business.
- **Pages must be enabled by hand**, and until it is, the workflow will
  fail at the deploy step on `main`. That is a visible failure rather
  than a silent one, which is the right way round.

## Verification

1. `docs/manual/*.md` -- every page is in the nav, in `llms.txt`, and
   linked from `index.md`. The CI check passes, and fails when a page is
   added without listing it.
2. `actions/jekyll-build-pages` builds the site with no warnings.
3. The site renders at the Pages URL, with the sidebar, the `/` filter
   and `Escape` to clear it behaving as nixarchy's does.
4. Every code path a page claims is checked against the source at the
   commit the manual is written from -- specifically the numbered claims
   in §4, each of which cites a file and line in the page that makes it.
5. Every screenshot is re-captured from the merged tree, and the
   selection files are checksummed before and after the capture run to
   prove nothing was installed.
6. `README.md` contains no instruction that the manual also contains, and
   links to it.
7. A page added without a nav entry fails CI -- tested by adding one,
   watching it fail, then listing it.
