# Spec: a faster tour, under a minute, that tells one story

The intent's four open questions were answered "yes to all". Two were
either/or, so the readings taken are written down here to be approved or
corrected rather than assumed: **webm with a GIF fallback**, **a tighter
capture rather than sped-up footage**, **the lazygit story**, and **a
committed capture script**.

## Design

### The story, as scenes

One reader, one want: *I want lazygit, I don't know if it's in nixpkgs, and
I don't want to open an editor.* Every tab is visited because the story
passes through it, not because a list is being read out.

| # | Scene | Shows | Budget |
|---|-------|-------|--------|
| 1 | Keybind opens the panel on **Apps**, already populated | it starts from the keyboard, not a terminal | 4s |
| 2 | `TAB` to **Services**, one service toggled on | a service is a row like anything else | 5s |
| 3 | `TAB` to **Selection** -- the toggle is already sitting there | queued, not applied | 5s |
| 4 | `TAB` to **Options**, search `openssh`, open the form on a boolean | options are managed here too, with a real form | 9s |
| 5 | `TAB` to **Drafts** -- the option just set is waiting | the sixth tab, the one the old tour never had | 5s |
| 6 | `TAB` to **Flakes**, a flakeref typed, its packages listed | packages come from elsewhere too | 8s |
| 7 | Back to Apps, `/lazygit`, exact match first, `SPACE` queues it | the actual want, answered | 10s |
| 8 | **Selection** again: three queued rows, none built | the claim the tool is built on | 6s |
| 9 | The bar widget, showing the same count | it is visible without the panel open | 4s |

Nine scenes, 56 seconds of budget, 4 seconds of headroom under the limit.
The budget is a table in the script, not a comment, so a scene that runs
long fails a check instead of quietly pushing the tour past a minute.

Scene 7 arrives at 41s rather than opening the tour. The reason is that the
queue-then-apply claim only lands once the reader has seen what a queue
is; opening on the search makes it a search box demo. If review disagrees,
moving scene 7 to the front is a row swap in the table.

Nothing is applied. The tour ends on three queued rows, which is the
honest ending and also means the capture alters no machine state.

### The capture: `tools/record-tour.sh`

First file under `tools/`. It exists because the last capture's hard-won
desktop knowledge is prose in a merged plan
(`plan/2026-09-18-14-manual.md:238-249`) and prose does not stop the next
person repeating five failed attempts. Each lesson becomes a precondition
the script refuses to proceed without:

- **The panel draws on every monitor, only the focused one takes keys.**
  The script picks a monitor the terminal is *not* on, `hyprctl dispatch
  focusmonitor`s it, and records that output's region.
- **`SUPER+ALT+N` is a toggle, so a tour can open by closing.** The script
  never guesses: `omarchy-shell shell listPlugins` reports `active` per
  plugin, and it is read before and after every toggle.
- **A shell call between keystrokes raises the calling terminal.** The
  script makes no foreground call once recording starts. Keystrokes are
  `wtype`; the beats are `sleep`; nothing else runs until the recorder
  stops.
- **A stale index carries no `unfree` or `broken` flags**, which would make
  the tour contradict the pages around it. Freshness is checked up front
  and the script stops rather than recording a lie.

It refuses to start when the working tree's selection differs from what it
saved, so an interrupted run cannot be papered over. On exit, trapped, it
restores `~/.config/nixarchy/apps.nix` and `services.nix` from copies taken
before the first keystroke, and closes the panel.

Tools, all present on this machine and all checked before use:
`wl-screenrec` (there is no `wf-recorder` here), `ffmpeg`, `wtype`,
`hyprctl`, `jq`. `gifski` is absent, so the GIF goes through ffmpeg's
`palettegen`/`paletteuse`.

### The two outputs

`wl-screenrec` writes lossless-ish source to the scratch directory; ffmpeg
produces both artifacts from that one take, so they can never drift:

- `docs/img/tour.webm` -- VP9, the version the pages show.
- `docs/img/tour.gif` -- same take, same path as today, 12fps, width 620 to
  match the current asset. Kept so that every context a GIF works in and a
  video does not -- and any reader whose browser refuses the webm -- still
  sees the tour.

`docs/index.md:13` and `docs/manual/getting-started.md:71` change from a
bare image to a `<video>` with the GIF inside it as fallback content, and
their captions stop saying "five tabs".

## Alternatives rejected

- **Speeding up the existing 84s footage.** Cheapest, and it would hit 60
  seconds. Rejected because it still shows five tabs: the recording is
  wrong, not merely long, and re-timing wrong footage produces a fast wrong
  tour.
- **Sped-up new footage.** Fits more in, but shows a panel moving at a
  speed no hand could drive, which oversells how the tool feels. Post-speed
  stays available for one genuinely dull span (an index rebuild), and that
  span is not in this tour.
- **A hand-driven re-cut with the keystrokes only written in this spec.**
  That is what happened last time. The keystrokes were known; the desktop
  was the problem, and a document cannot refuse to run when a precondition
  is unmet.
- **`asciinema`.** Tiny, diffable, scriptable -- and unable to record a QML
  panel, which is not a terminal.
- **Dropping the GIF once the webm exists.** The GIF is what works in
  contexts that will not play video. It costs one ffmpeg invocation over a
  take that has already been made.
- **A tab-by-tab tour, only faster.** Rejected by the intent: it teaches
  the tab names and not the reason to open the thing.

## Risks

- **The capture needs this desktop.** Hyprland, the shell running, the
  plugin enabled, a fresh index. CI cannot cut this recording, so the
  script's checks are the only thing standing between a bad take and the
  docs. It is run by hand on this machine and nowhere else.
- **A wrong take that looks right.** The last pass caught a bad screenshot
  only by reading the saved file. Same rule here: frames are extracted from
  the finished take and read before anything is committed.
- **Weight.** A 56-second GIF under 2.5 MB is a tight budget; the webm will
  be a fraction of it, the GIF is the one at risk. If it cannot be met at
  12fps and width 620, the frame rate drops before the tour loses a scene,
  and the number that was actually achieved is recorded in the plan's
  deviations.
- **The machine.** The script writes to `~/.config/nixarchy/` by driving
  the panel, and restores it. If it is killed uncatchably, the selection is
  left with the tour's toggles in it -- queued, never applied, so nothing
  is installed, and the copies it took are left in the scratch directory to
  restore from by hand.
- **`wtype` typing into the wrong surface.** Mitigated by focusing the
  monitor first and by reading `active` before toggling, but it remains the
  most likely cause of a bad take. It shows up as a wrong take, not as a
  changed machine.

## Verification

- `ffprobe` on both artifacts: duration under 60 seconds.
- `ls`: `docs/img/tour.gif` no larger than the 2.5 MB it is today.
- The scene table's budget sums under 60 in the script's own check, so the
  limit is enforced before a recording is ever made.
- Nine frames extracted, one per scene, and read: six distinct tab names
  across them, `lazygit` present as an exact first match, and the closing
  Selection showing queued rows with nothing built.
- `git diff --stat main -- bin/ '*.qml'` is empty. A usability problem
  found while driving the panel becomes an issue, as #17 did, not a change
  smuggled into a documentation pass.
- `~/.config/nixarchy/apps.nix` and `services.nix` identical, by checksum,
  before and after the run.
- Both referencing pages render the video with the GIF fallback, and
  neither caption claims a tab count that is not six.
