# Intent: the card responds to the pointer and shows work as motion, and the Selection tab loads without a binding loop

Builds on #55 (`fix/55-row-hierarchy-contrast`, approved, not merged). #55
lands first; this task starts from its `Card.qml`. Line numbers below are
`main` (`d3aabd3`), with #55's in brackets where they differ.

## Problem

#55's intent named "the card feels static" as a problem and asked for "the
cursor and hover respond, and running work is visible as motion". At #55's
intent approval that part, and tab counts, were split off to here (#56;
`spec/2026-10-11-55-row-hierarchy-contrast.md:9-11`).

**1. Nothing answers the pointer (#56).**
A row's `MouseArea` takes a click and nothing else (`Card.qml:132` [`:161`]):
no `hoverEnabled`, no hover colour. Tabs are the same (`:55` [`:81`]). The
only way to see which row a click will hit is to click it.

**2. The cursor jumps (#56).**
The highlighted row is not a `ListView` highlight. Each row paints itself
`selectedBackground` when it is current (`:130` [`:159`]), so the colour
switches in one frame. `highlightMoveDuration: 0` (`:115` [`:144`]) cannot
fade it, because no `highlight` item exists for it to move. Whether it also
paces the view's scroll under `highlightRangeMode: ListView.ApplyRange`
(`:120` [`:149`]) is not checked; raising it could change how the list scrolls
under a held arrow key.

**3. Work in progress is one word (#56).**
While a write runs, the footer's key hint is replaced by `working…`
(`:369` [`:475`]). It is static text in the same place and colour as the hint,
so a write that takes seconds looks the same as one that has stalled. A
`flake add` makes three Nix calls, each allowed up to two minutes. Inspecting
a flake (`PkgModel.qml:443-450`) sets `inspecting`, not `busy`, and shows only
the static text `looking at …`.

**4. Tabs do not say how much is in them (#56).**
A tab label is its name and nothing else (`:59-68` [`:85-94`]). How much
the user's selection holds is only seen by opening Selection. How much is
queued is only in the footer (`:340` [`:446`]) and on the bar. On `main`,
`PkgModel.queued` starts at 0 (`PkgModel.qml:47`), so "unknown" and "nothing
queued" look the same. #60 (unmerged) adds a Queue tab and an unknown state
(`queued: -1`), which is where a queued count would sit.

While a query is typed, the Selection tab lists search results instead of the
selection (`PkgModel.qml:87`, `:91`), so the number of rows on screen is not
always the size of the selection.

**5. Showing the Selection tab logs a binding loop (#57).**
The scope line under the tabs (`Card.qml:90-101` [`:117-128`]) sets
`height: visible ? implicitHeight + Style.space(6) : 0` on a `Text` with
`wrapMode: Text.Wrap`. When the Selection tab is shown, Qt logs "Binding loop
detected for property height". It has been on `main` since before #55. #55's
`test_preview_hidden_without_text`, the first test to set `tab = 2`, shows it
as a QWARN. The test still passes, so nothing fails on it.

## Proposed outcome

- A row or a tab under the pointer, other than the current one, looks
  different from the rest. Moving the pointer never moves the keyboard
  cursor.
- Moving the cursor fades the highlight from one row to the next, briefly,
  rather than jumping.
- While a write is outstanding, the card shows it with motion, not only a
  word. This says that a write is waiting for an answer, not that it is
  making progress. The motion stops when the write ends, with an answer or
  without one (`PkgModel.qml:247`).
- The Selection tab label shows how many packages are in the user's
  selection, whatever the search shows. If #60 lands first, the Queue tab
  shows how many changes are queued. A count that is not known is never shown
  as 0.
- Showing the Selection tab logs no binding loop. A test fails if it comes
  back.

## Affected users and systems

- Everyone using the menu or the bar card. Most noticed by mouse users and
  by anyone waiting on a slow write.
- `Card.qml` (rows, tabs, scope line, footer). `PkgModel.qml` if a count is
  not yet exposed there.
- `tests/qml/tst_card.qml` and the `Style` stub in
  `tests/qml/imports/qs/Commons/Style.qml`.
- Docs screenshots in `docs/img/` if the tab labels change.

## Constraints

- #55's rules hold: every colour is an Omarchy theme token, no appearance
  settings, no new dependencies, the summary width stays measured (#45, #53).
- Keyboard-first behaviour does not change: same keys, same focus rules.
  Hover is a hint, never a selection.
- Every animation honours the shell's own switch. Omarchy's `Style` has
  `reduceMotion` and `Style.duration(ms)`, which is 0 when the user turns
  Hyprland animations off (shell `Commons/Style.qml:360-367`). With motion
  off, changes are instant and nothing animates, but hover, counts and a
  visible busy state remain.
- Motion is short and never delays input or the answer it decorates.
- No new process calls. Counts come from what `state` and `pending` already
  return.
- Tests must not depend on animation timing.

## Open questions

1. **Order against #60.** The queued count belongs on #60's Queue tab, which
   is not merged. Recommended: land #55, then #60, then this. If this goes
   before #60, the queued count waits for a follow-up.
2. **Does motion replace `working…`?** #56 asks for a busy edge "instead
   of the word". Recommended: keep the word beside the motion, so the busy
   state reads the same with motion off and to anyone who does not notice
   an edge. Where the motion sits is for the spec.
3. **Does inspecting a flake count as busy?** It is slow network work, but
   not a write. Recommended: yes, it gets the same motion, since the user
   waits on it the same way.
