# Intent: the QML layer is checked by something other than my eyes

## Problem

#44 gave the QML layer a syntax gate. It would have caught **none** of the
four defects #43 fixed, because those were logic: a stale write response
closing a form the user had just reopened, a mode surviving a tab change and
swallowing keystrokes, a shared `Process` silently dropping a read, and a
process that could die leaving the panel refusing every later write.

There are 187 adapter assertions and **zero** for ~2300 lines of QML.

So every UI change merged today -- #42, #43, #45 -- was verified by eye, by
hand, on one machine. That is not a theoretical weakness; it failed four
times in a day:

- A verification run for #43 was **lost entirely** to a collision with
  another session driving the same desktop. The capture came back showing a
  different plugin's panel.
- A black screen mid-test looked like my own QML until the journal showed a
  Home Manager activation had restarted the shell.
- In #45, a row that appeared to show the exact defect being fixed was
  **truncated in the search index**, upstream of any rendering. Cropping the
  screenshot and querying the adapter is what settled it.
- The `OptionForm` `Flickable` from #42 is **still unverified in a running
  shell**, because reaching it needs a raised text size and that command
  segfaults quickshell (nixarchy#847).

Three of those were near-misses that a wrong conclusion could have ridden
out of. The fourth is an unverified claim sitting on `main` right now.

## Proposed outcome

- A defect of the kind #43 fixed fails a check before it reaches a desktop.
- The check runs without a display, without `/etc/nixarchy`, and without the
  omarchy shell -- so it can run on a pull request and on a machine nobody
  is using.
- A failing assertion fails the build, rather than printing a warning.
- The behaviours that actually broke this month are the ones asserted, not
  a set of cases invented to look thorough.
- When a future change to this layer is verified by eye, that is a choice
  rather than the only option.

## Affected users and systems

- Contributors. No runtime behaviour changes; nothing a user of the plugin
  can see.
- New files under `tests/`; `flake.nix` for the check; possibly
  `.github/workflows/ci.yml`.
- No change to `Menu.qml`, `Card.qml`, `OptionForm.qml`, `PkgModel.qml` or
  `Panel.qml` -- if a file has to change to become testable, that is a
  design question to raise separately, not something to smuggle in here.

## What was measured before filing this

An intent that promises a harness I cannot build is worse than none, so the
feasibility was settled first:

| | |
| --- | --- |
| `qmltestrunner` in `qt6.qtdeclarative` | present, already in the devShell |
| headless run (`QT_QPA_PLATFORM=offscreen`) | works |
| passing suite | exit 0 |
| **failing suite** | **exit 1** -- a real gate |
| a stub `qs.Commons` module | resolves, and its members are usable |

The shell surface these files touch is small: **9 distinct `Style.*`
members, 11 `Color.*`, and `Border`**. And the split is favourable:

| file | needs from the shell | carried |
| ---- | -------------------- | ------- |
| `PkgModel.qml` | **nothing** but `Quickshell.Io` | all three of #43's async/state bugs |
| `Card.qml` | `Style`, `Color` | #45's width arithmetic |
| `Panel.qml` | `Style`, `Color` | -- |
| `Menu.qml` | + `Border`, `BorderSurface`, `PanelWindow`, `TextField` | #43's naming leak |
| `OptionForm.qml` | + `Dropdown`, `NumberField`, `Toggle` | #43's stale-write bug |

**The two files that carried today's real bugs are the two cheapest to
test.** `PkgModel` needs no `qs.*` stubs at all -- only fakes for `Process`
and `StdioCollector`, which is precisely what makes it drivable: a test can
hand it a canned adapter answer and assert what the model did with it.

## Constraints

- Must not change the five QML files to make them testable. A test that
  requires the subject to be rewritten is testing the rewrite.
- Must not assert the shell's behaviour. The stubs exist to let our code
  run, not to pin down what `Style.space()` returns. An assertion that would
  fail because omarchy changed is a false alarm and will be deleted.
- Must fail the build on a failing assertion, like every other check here.
- Must not need a display, `/etc/nixarchy`, the omarchy shell, or razer.
- Must not grow into a second source of truth about the panel's behaviour.
  Where a test and the code disagree about intent, the code and its comments
  win until someone decides otherwise.
- Proportionate to a personal project. Coverage of what broke, not of
  everything that could.

## Open questions

1. **How far?** `PkgModel` alone is most of the value for a fraction of the
   stubs -- it held three of the four #43 defects and needs no `qs.*` fakes.
   Adding `Card` costs two small singletons. Adding `Menu` and `OptionForm`
   costs five widget stubs and buys the stale-write and naming-leak cases,
   which are the two most user-visible defects of the month.

2. **Where is the line on stub fidelity?** A `Process` stub that never
   emits `exited` cannot test the `onExited` fix from #43; one that models
   exit codes starts to be a re-implementation of Quickshell. The fix it
   exists to protect is the one that makes the `busy` interlock safe, so
   getting this wrong quietly removes the point.

3. **CI, or razer?** It needs nothing razer has, which argues for CI. But it
   adds a Qt runtime to every pull request, and #44 has just established
   that CI is worth keeping fast and quiet.

4. **Does the unverified `Flickable` from #42 get covered here?** It is the
   one outstanding claim on `main`, and a harness that cannot reach it
   leaves the most obvious gap open. Whether a headless `TestCase` can
   observe `contentHeight` and clipping meaningfully is unknown and worth
   probing before promising.
