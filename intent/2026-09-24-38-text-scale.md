# Intent: menu text follows the desktop's text size

## Problem

The menu multiplies every shell font token by a flat `1.45`. `Menu.qml:35`
and `Card.qml:19` declare `readonly property real textScale: 1.45`,
`OptionForm.qml:56` declares the same property at `1.0` and is handed `1.45`
by `Menu.qml:469`, and each of the three files carries its own copy of
`function px(base) { return Math.round(base * root.textScale) }`.

The tokens it multiplies already follow the desktop's text size. `[font]
base-size` in `~/.config/omarchy/shell.toml` -- what `omarchy display text
size` sets -- is the root of every `Style.font.<token>`, and `Style.space()`
scales by the same factor. So the multiplier does not make the menu
scale-aware. It makes the menu 45% larger than the rest of the shell at
every size, permanently.

Two consequences the user sees:

1. The menu never matches the bar or the other panels, at any text size.
2. The multiplier reaches only the text this plugin draws itself. The shell's
   own `qs.Ui` widgets hardcode their sizes -- `Ui/TextField.qml:41` is
   `Style.font.body` -- so the search field and all four `OptionForm`
   controls render at 1x inside a 1.45x surface. The search box is visibly
   smaller than the list rows beneath it.

Monitor scale is not involved. QML sizes are logical pixels and the
compositor applies the output scale, so text and window already follow a
2x or fractionally-scaled monitor correctly.

The same multiplier exists in four sibling menus.
`nixarchy-flatsnap` fixed its copy in olafkfreund/nixarchy-flatsnap#9
(PR #14); this issue is the follow-up that spec listed for this repo.

## Proposed outcome

- No flat multiplier anywhere in this plugin's QML. Text size comes from the
  shell's `Style` tokens alone.
- The menu still reads larger than the bar, but by a scale-aware step -- a
  bigger token -- rather than a multiplier.
- `omarchy display text size 9..20` re-flows the menu live, and at every
  setting the menu keeps a fixed relationship to the rest of the shell
  instead of drifting 45% away from it.
- The search field and the `OptionForm` controls are the same size as the
  text around them.
- A check in `nix flake check` fails if a multiplier is reintroduced, so
  this does not come back.
- The option form scrolls instead of painting outside the card, so raising
  the desktop text size cannot push its controls out of reach.

## Affected users and systems

- Anyone running the `nixarchy.pkg` plugin. Purely visual; no config file,
  no adapter behaviour, no NixOS state is touched.
- Files: `Menu.qml`, `Card.qml`, `OptionForm.qml` (34 `px()` call sites
  across the three, resolving to only three distinct tokens -- `caption`
  x21, `body` x9, `subtitle` x1), and `flake.nix` for the new check.
  `Panel.qml` and `PkgModel.qml` contain no `px()` and are unaffected.
- Verification host is **razer**, per repo convention. Never p620.

## Constraints

- Must not reintroduce a second scale under a different name. The failure
  mode being removed is "a number that multiplies a token", whatever it is
  called.
- Must keep following a theme that pins a token in `shell.toml`. Anything
  that computes a fixed pixel size defeats the point.
- Must not take a factor from the monitor (`devicePixelRatio`). The
  compositor already applies it; multiplying again doubles it.
- Should use the same tokens `nixarchy-flatsnap` chose, so the five nixarchy
  menus agree. Deviating needs a reason recorded in the spec.
- No upstream omarchy change in this task. A shared `Style.font.menu` token
  would be cleaner but is a different repo.
- Text will get slightly smaller at the default size. That is accepted, not
  a regression to mitigate.

## Decisions

Answered by the approver on 2026-09-24. Recorded here; the design that
follows from them belongs in the spec.

1. **`body` steps up to `heading`, and the flattening is accepted.**
   The three tokens in use map as:

   | today | sites | becomes | at base-size 12 |
   | ----- | ----- | ------- | --------------- |
   | `caption` x 1.45 | 21 | `title` (x1.167) | 15px -> 14px |
   | `body` x 1.45 | 9 | `heading` (x1.333) | 17px -> 16px |
   | `subtitle` x 1.45 | 1 | `heading` (x1.333) | 19px -> 16px |

   Two tiers total, which is what `nixarchy-flatsnap` ended up with. The
   cost is accepted deliberately: the option path header
   (`OptionForm.qml:303`) stops being larger than the body text beside it.

2. **The shell's `Dropdown` needs no change, upstream or here.** It
   hardcodes `Style.font.caption`/`body` and exposes no size property, but
   once the multiplier is gone that is the same token everything else uses,
   so the mismatch resolves itself. The defect was the multiplier, not the
   `Dropdown`. No omarchy issue filed.

3. **The `OptionForm` overflow is fixed in this task.** `OptionForm.qml:295`
   is a `Column` with no bottom anchor, no `Flickable` and no `clip`, inside
   a `FocusScope` and a `BorderSurface` that also do not clip -- so once
   content exceeds the card it paints outside the border onto the scrim.
   Raising `base-size` to 16 is what makes that happen, which is exactly what
   this task invites users to do. Shipping the text change without it would
   be half a job. `Card.qml:211`, which can compute a negative width on a
   flake row, is **not** folded in -- it is a pre-existing arithmetic bug
   with no dependency on text size.
