# Intent: the panel says how old the search index is and what changed, and a failed reindex says why

## Problem

Split out of #60 (approved intent, open question 4).

**The index goes stale without the user noticing.** On this machine (checked
2026-11-16), `~/.cache/nixarchy/index.tsv` was written on 2026-11-02, 14 days
ago. Six of the seven inputs in its stamp have changed since: nixpkgs,
`options.json`, the app index, the app table, the flatpak rows and the
new-package row. Only the walk is the same. Nothing rebuilt it. The panel's
only sign is one line, "index stale — r to rebuild" (`Card.qml:356-357`).
It does not say whether the index is an hour old or a month old, or that the
package and option lists are from an older nixpkgs.

The adapter knows only a yes or no. `index_stale` (`bin/nixarchy-pkg:257-265`)
compares the stamp file with the paths `nixarchy-search` would index now,
and returns a status. `state` and `search` pass that on as one boolean,
`indexStale`. The stamp holds one store path per input, line by line, in the
order of `stamp_key` in `nixarchy-search`. So the adapter could say which
inputs changed, and the index file's age, but it throws both away.

This matters for more than freshness. An index built before nixarchy #493
carries no unfree or broken flags at all, so every package reads as free
(`docs/manual/packages.md:71-72`, and the comment at
`bin/nixarchy-pkg:1451-1453`). Today the only sign of such an index is the
same "stale" line.

**A failed reindex hides its reason.** `cmd_reindex`
(`bin/nixarchy-pkg:1454-1466`) runs `nixarchy-search --reindex` with all
output sent to `/dev/null` and `|| true`. It then decides success only from
the stamp, and says "the index is still stale -- run nixarchy search in a
terminal to see why". The reason is thrown away, even though
`nixarchy-search` prints one when indexing fails ("indexing nixpkgs failed;
the end of …index-errors.log", its lines 119-121). The user has to run
another command to find out. The output cannot simply be passed through
either. With no terminal, `nixarchy-search` builds the index and then fails
at its picker, which prints its own noise. The issue and the adapter's
comment (`bin/nixarchy-pkg:1456-1459`) say it then exits non-zero even after
a good reindex. The installed `nixarchy-search` no longer does: its picker
call ends `|| exit 0` (its line 234). Either way, the exit status says
nothing about whether the index came out fresh, so the stamp stays the
judge. `index-errors.log` is also noisy: on this
machine it starts with Nix evaluation warnings
("'coqPackages' is deprecated…"), not errors.

**Nothing in the panel reindexes on its own.** `state` and `search` only
report staleness. The index is rebuilt when the user presses `r`, or runs
`nixarchy search` in a terminal, which rebuilds a stale index before opening
its picker (`nixarchy-search` lines 162-165). Whether a login hook or timer
elsewhere does it was not checked; on this machine nothing did for 14 days. The
issue records automatic reindexing (at login, or when the system generation
changes) as a separate decision.

## Proposed outcome

- When the index is stale, the panel says when it was built ("index built
  14 days ago") and, in a few words, what changed ("nixpkgs and the app list
  changed"). It still offers `r`. It does not claim to know how long the
  index has been stale, which the stamp cannot tell.
- When the index is missing, the panel says so, not "stale".
- When the age or the changes cannot be known (no stamp, an unreadable one,
  a format the adapter does not recognise), the panel says "stale" and
  nothing it cannot back up.
- A terminal user can get the same facts from `nixarchy-pkg state` and
  `search`.
- When a reindex leaves the index stale or missing, the answer says why,
  using `nixarchy-search`'s own words, trimmed to the lines that matter. A
  reindex that succeeded never shows the picker's no-terminal failure as an
  error.
- Whether anything reindexes automatically is decided under Open questions,
  not assumed.

## Affected users and systems

- Everyone who searches packages or options in the panel, and everyone who
  reads `nixarchy-pkg state` or `search` from a terminal.
- `bin/nixarchy-pkg` (`index_stale`, `cmd_state`, `cmd_search`,
  `cmd_reindex`), `PkgModel.qml` (`indexStale` and the reindex answer),
  `Card.qml` (the stale line), `docs/manual/{packages,troubleshooting,from-a-terminal}.md`.
- Outside this repo: `nixarchy-search` in nixarchy owns the stamp format,
  the index and `index-errors.log`. This task reads them. It does not change
  them unless an open question decides it should.
- Overlaps `feat/60-truthful-queue` in `PkgModel.qml`, `Card.qml` and
  `from-a-terminal.md`.
- Verification host is **razer**, per repo convention.

## Constraints

- The adapter's JSON contract may gain fields but must not change
  `indexStale` (`docs/manual/from-a-terminal.md`, "What is stable").
- Reading the age and the changes must stay cheap. `state` runs on every
  panel open, so this must not evaluate Nix or read the 60 MB index.
- Must not depend on the order or meaning of the stamp's lines beyond what
  `nixarchy-search` defines. If that format changes, the panel falls back to
  "stale" and says nothing wrong.
- A reindex updates only the user's cache (`${XDG_CACHE_HOME:-~/.cache}/nixarchy`,
  plus temp files). It needs no root and no rebuild, never changes the
  user's Nix files, and that stays true.
- No new runtime dependency.
- If anything reindexes automatically, it must not slow login noticeably or
  compete with an apply. (A reindex the user asks for is allowed during an
  apply today, `PkgModel.qml:347-348`, and this task does not change that.) It is about a minute of CPU and memory, and it ran
  out of memory once (the comment at `nixarchy-search` lines 116-117).

## Open questions

1. **Automatic reindexing.** Options: (a) never, and the panel only says
   how old the index is; (b) a user systemd unit or timer that reindexes
   after login or when `/run/current-system` changes; (c) the panel starts a
   background reindex when it opens and finds the index stale.
   Recommended: (a) here. Raise (b) in nixarchy, which owns `nixarchy-search`
   and the system modules, because a plugin should not add services.
2. **How to name what changed.** The stamp lines are store paths. Recommended:
   name the inputs in plain words (nixpkgs, options, app list, flatpaks), and
   do not attempt version numbers. Should "nixpkgs changed" show the old and
   new nixpkgs revision when the path carries one?
3. **Which errors to surface.** Recommended: when the index is still stale
   after a reindex, show the last lines of `nixarchy-search`'s stderr from
   that run, without the picker's no-terminal failure, and point to
   `~/.cache/nixarchy/index-errors.log`. Do not parse the log for warnings.
4. **Ask nixarchy to separate reindex from the picker.** Today a reindex
   with no terminal still reaches `fzf`, and its exit status is 0 whether or
   not the picker ran. A reindex-only mode that never opens the picker and
   exits non-zero when indexing fails would make the status mean something.
   Recommended: file it in nixarchy, and keep the stamp check here either
   way.
