# Intent: the panel's state matches what actually happened

## Problem

Three defects in the QML layer, all the same shape: the panel holds a state
that no longer matches reality, and acts on it. None involves the adapter --
#39 and #41 cover that side. These are reachable by ordinary use.

**1. Closing a form mid-write drops a result that already landed on disk.**
`OptionForm.qml:255` records `writingPath` when `commit()` fires
`writeProc`, and `:98` uses it to ignore a response meant for a form the
user has moved on from. But `finish()` (`:131-140`) clears `open`, `option`
and `path` and never clears `writingPath`.

Press RETURN then ESC inside the ~100-300ms `nix-instantiate --parse` takes,
and the guard at `:98` sees `!root.open` and returns. The value *was*
written -- the adapter had already copied the file -- but `model.refresh()`
at `:112` never runs, so the queued count and the option's state stay stale
until something else happens to refresh.

Reopen the *same* option before that response arrives and it is worse:
`begin()` sets `path` back to the same string and `open` back to true, so
`writingPath === path` again and the guard passes. The stale response then
runs `model.refresh()` and `root.finish()` (`:114`) -- **closing the form
the user has just reopened and is typing into**, with nothing to explain it.

**2. Naming a flake input survives a tab change and captures the keyboard.**
`setTab()` (`PkgModel.qml:198`) calls `disarm()` and
`invalidateInspection()` but never touches `naming`. `Menu.qml`'s handler
only intercepts Return and Escape while naming; Tab, Backtab and a click on
a tab header all fall through to `setTab()`.

Begin naming an input on Flakes, press Tab, and the view moves to Apps while
`naming` stays true. From there, typing no longer filters -- `setQuery()`
(`:297`) redirects every keystroke into `namingName` -- and RETURN does not
toggle the row under the cursor but calls `declareAs()` with the stale
`namingRef` from the abandoned Flakes session. A `cancelNaming()` already
exists at `:507`; `setTab` simply never calls it.

**3. One `Process` is shared by two readers, so one of them is dropped.**
`PkgModel.qml:210` declares `_reader`, used by both `refresh()` (`:277`,
`state`) and `runSearch()` (`:309`, `search`). Every other operation has its
own `Process` precisely so one cannot clobber another -- the comment at
`:208-209` says so. Assigning `.command` while `running` is already true is
a no-op, so the second caller's command never runs.

Type a query on Selection or Options -- a grep over the full index, not
instant -- and while it is in flight press `r` to reindex or let an apply
finish. Both end in `refresh()`, and that read is silently dropped: the
search returns fine, but the state read never happens. The footer keeps
saying "index stale -- r to rebuild" after a successful rebuild, and the
catalogue can keep showing pre-apply state.

**4. Found while confirming the above, and the same family.**
`OptionForm.qml` has **no `onExited` on any of its processes**. Every path
depends on `StdioCollector.onStreamFinished`. If the adapter cannot start --
missing, not executable, killed before it writes -- that signal may never
arrive, and `model.busy` is left `true` at `:252`, which refuses every
subsequent write with "still writing" until the panel is reopened. Raised
independently by two of the reviews that produced #43.

## Proposed outcome

- A write that reaches the disk is always reflected in the panel, whether or
  not the form that started it is still open.
- A response that arrives after the user has moved on is discarded, and
  cannot be mistaken for a response to whatever they are doing now --
  including when they have returned to the same option.
- No form closes itself except when the user closes it or a write it is
  still showing completes.
- Changing tab leaves no mode behind. Keystrokes go where the visible tab
  says they go.
- A read that is asked for happens, or is reported. Two reads in flight do
  not silently cancel one another.
- A process that dies without answering unblocks the panel and says so,
  rather than leaving it refusing writes.

## Affected users and systems

- Anyone using the Options tab or declaring a flake input -- defects 1 and 2
  need only ordinary timing and an ordinary keypress.
- `OptionForm.qml` (1, 4), `PkgModel.qml` (2, 3). `Menu.qml` may need a
  companion change for 2 depending on where cancelling belongs.
- No adapter change, no config format, no JSON contract, no NixOS state.
- The QML layer has **no tests and no lint in CI** (#44), so nothing here
  will be caught automatically. Verification is by hand.
- Verification host is **razer**, per repo convention. Never p620.

## Constraints

- Must not reintroduce a second source of truth. The existing
  `_inspectToken` pattern (`PkgModel.qml`) already solves "ignore a stale
  answer" in this codebase; a different mechanism for the same problem is a
  cost, not a fix.
- Must not make `finish()` conditional on a write being in flight. A user
  who presses ESC must get their form closed; the fix belongs in what
  happens to the response, not in refusing the key.
- Must keep the guarantee added by #28 that the panel never reports a write
  it cannot confirm. Unblocking `busy` on a dead process must not be
  mistaken for reporting success.
- Must not require the live text-size sweep. `omarchy display text size`
  segfaults quickshell on this host (nixarchy#847, see
  `plan/2026-09-24-38-text-scale.md`), so any verification depending on it
  has to be designed out rather than written down.

## Open questions

1. **Token or flag?** Defect 1 can be fixed by clearing `writingPath` in
   `finish()`, which is one line but still leaves "same option reopened
   quickly" theoretically ambiguous. The codebase's own answer elsewhere is
   a monotonic token (`_inspectToken`). Is the extra machinery worth it
   here, or is the one-liner the right size?

2. **Where does a landed-but-unwatched write get reported?** After ESC, the
   write has happened and the panel does not know. Refreshing silently is
   the smallest fix, but the user pressed RETURN and saw nothing. Should the
   footer say so, and if so is that this task or a separate one?

3. **Who cancels naming?** `setTab()` calling `cancelNaming()` is the
   obvious fix, but `Menu.qml` owns the search field whose text is the
   half-typed name. Does the field need clearing in the same change, or does
   `setTab` already lead somewhere that does it?

4. **Scope of defect 4.** Adding `onExited` to `writeProc` is small. Doing
   it for `describe` too, and for the five processes in `PkgModel.qml`, is a
   broader sweep with the same justification. All of them, or only the one
   that can strand `busy`?
