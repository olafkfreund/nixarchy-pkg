# Intent: CI checks the things that actually break

## Problem

Nothing in this repo's CI is wrong. The problem is what it does not look at.

`.github/workflows/ci.yml` runs `nix flake check`, builds the plugin, and
asserts there are no symlinks, that the bar mark ships, and that every
manifest entry point exists. `nix flake check` runs shellcheck, a manifest
`jq` assertion, a hex-colour grep and, since #38, `no-text-multiplier`.

**None of it parses a line of QML, and none of it runs the adapter.**

**1. ~2300 lines of QML have no static check.** `nix build` is a
`runCommand` that copies the `.qml` files verbatim. A syntax error ships and
fails at runtime in the shell, where the symptom is a plugin that silently
never draws. `qt6.qtdeclarative` is already in the devShell and ships
`qmllint`; nothing invokes it.

This is not hypothetical any more. #43 fixed four defects in the QML layer,
and #42 restructured `OptionForm.qml` around a `Flickable`. Every one of
those changes was verified by hand, by eye, on one machine, because there
was nothing else to verify them with. The repo has been running its riskiest
edits through its least-checked layer.

Measured while framing this, because it changes the shape of the answer:
`qmllint` **exits 255 on a syntax error and 0 on a clean file**, and the 780
import warnings these files produce -- `qs.Commons` and `qs.Ui` come from
the host shell and cannot resolve here -- do **not** affect its exit status.
So the gate that has been missing costs one `runCommand`; it did not need
the import problem solved first.

**2. The adapter's own suite never runs on a pull request.**
`tests/adapter.sh` is 529 lines of careful coverage -- byte-exact
assertions, `md5sum` untouched-on-failure checks, a timing check that
distinguishes streaming from buffered output, faithful PATH-stubbing of
`nixarchy-apply`, and since #39 `stat`-based mode and symlink assertions.
None of it protects a PR.

This is deliberate and documented at `ci.yml:17-20`: the suite reads
`/etc/nixarchy`, which exists only on a nixarchy machine, and it self-skips
rather than passing vacuously. The consequence is still worth stating
plainly: **the 1332-line script that performs every write to a user's NixOS
configuration has no regression protection except somebody remembering to
run it on razer.** Today that happened because the work was about those
writes. It will not always be.

**3. Two subcommands have never been tested at all.** `draft new` /
`draft undraft` call external writers that create and mutate draft package
files -- the same risk class as `pkg add` and `flake add`, both well
covered -- and nothing verifies arguments are forwarded or a writer's error
surfaced. `reindex` likewise. The PATH-stub pattern they need already exists
in the file.

**4. CI builds only the runner's system.** `ci.yml` runs on
`ubuntu-latest`, i.e. `x86_64-linux`, while `flake.nix:8` declares
`[ "x86_64-linux" "aarch64-linux" ]`. `nix flake check` says so out loud
every run: `warning: The check omitted these incompatible systems:
aarch64-linux`. The aarch64 outputs are never evaluated, let alone built.
The derivation is a plain `cp` today, so the risk is low -- but the
declaration is a promise the repo does not keep.

## Proposed outcome

- A QML syntax error fails a pull request instead of a user's desktop.
- The adapter's existing tests protect a pull request, or it is written down
  why they cannot and what would have to change for them to.
- `draft` and `reindex` are covered to the standard `pkg add` and
  `flake add` already meet.
- Either every system `flake.nix` declares is checked, or it declares only
  what is checked.
- CI stays fast and quiet enough that a red run still means something. A
  check that cries wolf is worse than the gap it fills.

## Affected users and systems

- Contributors and future-me. No runtime behaviour changes; nothing a user
  of the plugin can see.
- `.github/workflows/ci.yml`, `flake.nix`, `tests/adapter.sh`. Possibly new
  fixture files if item 2 is taken up.
- No adapter logic, no QML, no config format.

## Constraints

- Must not turn 780 pre-existing `qmllint` warnings into a gate. Those come
  from imports that cannot resolve outside the shell, and failing on them
  would mean disabling the check within a week. Syntax is the contract.
- Must not weaken `tests/adapter.sh` to make it run in CI. A suite that
  passes vacuously is worse than one that honestly skips -- that reasoning
  is already recorded at `ci.yml:17-20` and stands.
- Must not add a dependency on the omarchy shell to build or check this
  repo. The plugin is installed into that shell; it is not built against it.
- Proportionate to a personal project. The existing tests are better than
  typical, and the answer to every gap is not necessarily "add a check".
- Verification host is **razer**, per repo convention. Never p620.

## Open questions

1. **Does the adapter suite get fixtures, or stay a manual gate?** Its three
   templates are small -- 139 lines total, 84 catalogue rows -- so
   committing copies is easy. But the suite deliberately builds from *this
   machine's own catalogue* (`fresh_config()`, and the comment above it), so
   frozen fixtures would test a frozen catalogue and stop catching drift
   against nixarchy's real one. Which risk is worth more: no CI coverage, or
   CI coverage of a catalogue nobody ships?

2. **Is a partial run worth it?** Much of the suite builds its own
   `mktemp -d` fixtures and needs no `/etc/nixarchy` at all -- the flake
   sections especially. Splitting it so the machine-independent half runs on
   every PR is more work than fixtures but keeps the catalogue honest.
   Worth the split, or all-or-nothing?

3. **aarch64: build it, evaluate it, or stop claiming it?** Building needs
   emulation in CI for a derivation that only copies files. Evaluating the
   outputs is nearly free and would catch a real breakage. Dropping the
   system from `flake.nix` is the honest third option if nobody runs this on
   aarch64.

4. **Does `qmllint` get the Qt import path (`-I`)?** Without it even
   `QtQuick` fails to resolve, though the exit code is unaffected. With it,
   only the two host-shell modules remain unresolvable and the output is
   readable by a human debugging a failure. Cost is one line; the question
   is whether the check should aim to be readable or only to be a gate.
