# Intent: a real manual, on a Pages site in nixarchy's style

## Problem

The documentation is `README.md` -- 168 lines -- and the `?` key sheet.
There is no `docs/` directory, no site, and GitHub Pages has never been
configured for this repository.

Between them the two existing documents answer one question well: which
key does what, for somebody who already knows what the panel is. The key
sheet is genuinely good at that, and it is in the right place, because it
is on screen at the moment the question is asked.

Neither answers the questions somebody actually has:

- What is this, and why is there a menu row for it?
- I installed nixarchy as a flake input. Does this work for me?
- What is the difference between an app, a package and an option? They
  all look like rows.
- I picked something. Nothing happened. Did it work?
- What is that number in the bar?
- I set an option and it wrote a comment instead of a value. Why?
- Can I use any of this from a terminal?

The README does not answer these because it is not shaped to. It is a
project README -- what this is, what it is not, how to install it -- and
lengthening it would produce a worse README rather than a manual.

The gap has a specific shape: **every surface is undocumented except by
its keys.** The bar widget, the six tabs, the option form's five widgets,
the apply log, and the whole adapter CLI -- which is now a usable
terminal tool and is mentioned nowhere -- have no prose anywhere
describing what a person does with them or what happens next.

There is also a duplication that will get worse. nixarchy's own manual
has `manual/other-packages.md`, which describes the Install menu, the
search picker and the selection files. That page is about the nixarchy
CLI; this panel is a different front end to the same writers. Left alone,
the two will drift, and the reader who finds the wrong one first will be
the one who is wrong.

## Proposed outcome

Somebody who has just seen a menu row called Packages can open the
manual, find their own situation described, and get from there to a
package installed -- without reading the source and without asking.

Concretely, when this is done:

- `docs/` is a Jekyll site in nixarchy's own style: no theme gem, the
  layouts and one stylesheet being the whole of it, dark and monospace,
  with a sidebar whose order is stated rather than derived.
- GitHub Pages serves it, and the README links to it rather than trying
  to be it.
- Every surface has a page, and every page is written as what a person
  does: the bar widget, each of the tabs, the option form, applying, and
  the adapter from a terminal.
- Getting started covers **both** installation shapes, with the
  flake-adopter case first, because it is most people.
- The manual is explicit about the boundaries this project has already
  had to explain twice: that the package tab lists a selection rather
  than the machine (#11), and that options of some types get a commented
  scaffold rather than a widget.
- nixarchy's `manual/other-packages.md` and this manual point at each
  other rather than repeating each other.
- The README shrinks to what a README is for.

Afterwards, "how do I use this" has an answer that is not the source.

## Affected users and systems

- People meeting this for the first time, on either installation shape.
- `docs/` -- new: `_config.yml`, `_layouts/`, `_includes/`, `assets/`,
  and a page per surface.
- `README.md` -- reduced, and linking out.
- `.github/workflows/` -- whatever publishes the site, if a workflow is
  needed at all; GitHub Pages can build Jekyll from a directory without
  one.
- Repository settings: Pages has to be turned on, which is a change
  outside the tree and needs saying out loud rather than assuming.
- Not `bin/`, not the QML. This documents what exists. If writing a page
  shows that something is confusing, that is a finding to raise, not a
  change to slip in beside the prose.
- nixarchy's repository, if the cross-links are to be mutual. That is a
  change in another repository and cannot be made from here.

## Constraints

- **Must describe what has actually landed.** #11 renames the package
  tab, #4 adds a key to it, #3 adds a sixth tab and is not yet pushed.
  A manual written against an unmerged tree is wrong on the day it
  publishes. This is the scheduling constraint and it is the reason this
  cannot simply be written now.
- **Must not invent behaviour.** Every claim is checkable against the
  code or against a command that was run. The measurements this project
  has already made -- that a stale index reports every package as free,
  that the two channels share no store paths, that `nix flake show`
  cannot see inside `homeManagerModules` -- belong in the manual because
  they are what a person actually trips over.
- **Must match nixarchy's site structurally**, not merely visually. The
  same no-theme-gem arrangement, so what builds on Pages is what is in
  the directory, and somebody who knows one site can edit the other.
- **Must not duplicate nixarchy's manual.** Where a topic is theirs, link
  it.
- **Must not become a second source of truth for keys.** The `?` sheet is
  generated from `bin/nixarchy-pkg-keys` and is on screen when it is
  wanted. The manual explains what a key is *for*; it does not become a
  second table to keep in step.
- **Must not require a build step.** A contributor should be able to edit
  a page and see the change on Pages without a toolchain.
- Nothing published that the repository does not own: no screenshots of
  a real machine's package list, no flake paths from anyone's home
  directory.

## Open questions

1. **What does the manual describe, and therefore when is it written?**
   Three shapes: after #11, #4 and #3 all merge -- correct, and blocked
   on #3, which is still unpushed and conflicts with #11; after #11 and
   #4 only, with Flakes added later; or now against `main`, which
   documents a panel nobody will be running within the week. The middle
   option looks right and the approver should decide, because it decides
   the order of everything else.

2. **Does this live here or in nixarchy's manual?** A separate site is
   what the issue asks for and keeps the plugin's documentation with the
   plugin. The argument the other way is that a user does not know or
   care which repository a tab came from, and nixarchy's manual is where
   they will look first. A third shape -- this site exists and nixarchy's
   manual has one page pointing at it -- may be the honest one.

3. **How much of nixarchy's site is copied?** The layouts and stylesheet
   are small and readable, and copying them gives an exact match. It also
   forks them: a fix to nixarchy's CSS will not reach this site. Copy,
   or reference, or accept the fork and say so in a comment.

4. **Is the wordmark reusable?** nixarchy's masthead is block-drawing art
   with a stylesheet tuned to it -- the letter-spacing and line-height
   are documented as measured values that stop it rendering with seams.
   This project has its own mark (the drawn parcel, #10). Whether the
   site gets its own wordmark, borrows nixarchy's, or has neither.

5. **Does the adapter CLI get a page or a reference?** It has nine
   subcommands, it emits JSON, and it was built as the panel's back end
   rather than as a tool. Documenting it makes it a promise -- people
   will script against it, and its output becomes an interface that
   cannot change quietly. Worth deciding before it is written down, not
   after.

6. **Who turns on Pages?** It is a repository setting, not a file. This
   task can produce everything except that, and should say so rather than
   report a site that is not being served.
