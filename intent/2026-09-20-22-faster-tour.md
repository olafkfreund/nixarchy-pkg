# Intent: a faster tour, under a minute, that tells one story

## Problem

`docs/img/tour.gif` is the first thing a visitor sees on the docs index and
on the getting-started page. Three things are wrong with it.

**It is too long.** 84 seconds, 505 frames, 2.5 MB. Nobody watches 84
seconds of a package manager. The interesting part -- that a package is
queued and *not* installed until you apply -- arrives after a minute of
scrolling, by which point the reader has moved on.

**It is out of date.** Its captions say five tabs. `PkgModel.qml:28`
lists six: Apps, Services, Selection, Options, Drafts, Flakes. Drafts did
not exist when the gif was cut. A tour that omits a tab teaches the reader
the tool has one fewer surface than it does, and the caption beside it
states a number that is wrong.

**It is a feature list, not a story.** It walks tabs because the tabs
exist. A reader who has never run the tool learns what the tabs are called
but not why anyone would open it: that you can search all of nixpkgs from a
keybind, queue something, see it sitting in the Selection unbuilt, and
apply when you mean to.

There is also no way to re-cut it. No capture script was committed; the
existing gif was hand-driven and the capture fought the desktop through
five failed attempts, for reasons recorded in
`plan/2026-09-18-14-manual.md:238-249` -- the panel draws on every monitor
but only the focused one takes keys, `SUPER+ALT+N` is a toggle so starting
a tour with it closes an open panel, and any shell call between keystrokes
raises this session's terminal and steals the workspace. Those lessons are
prose in a merged plan and nothing enforces them, so the next re-cut pays
for them again.

## Proposed outcome

- A recording under 60 seconds that visits all six tabs.
- It reads as one continuous user story with a beginning and an end,
  not a tab-by-tab feature tour.
- The captions beside it in `docs/index.md` and
  `docs/manual/getting-started.md` match what it now shows, including the
  tab count.
- Re-cutting it is a command, not an afternoon: the keystroke sequence and
  the desktop preconditions live in the repository rather than in a merged
  plan's prose.

## Affected users and systems

- Readers of the docs site and the README -- the only people this is for.
- The capture needs a real Hyprland session with the panel built and the
  index fresh: a stale index carries no `unfree` or `broken` flags, which
  silently makes the recording contradict the pages around it.
- No machine state changes. The tour queues a package and must end without
  installing anything.

## Constraints

- Must be under 60 seconds.
- Must show every tab in `PkgModel.qml:28`, Drafts included.
- Must not install anything or leave the working machine altered; the
  selection is restored after the capture.
- Must not exceed the current 2.5 MB weight, which was itself chosen to sit
  under nixarchy's own demo gif. A faster tour that is a larger download is
  not an improvement.
- Must not change `bin/` or any `.qml`. If driving the panel exposes a
  usability problem, that is its own issue, as it was for #17.
- The old gif is replaced, not kept alongside; both referencing pages are
  updated in the same change.

## Open questions

1. **Format.** Stay with GIF, or move to a video (webm/mp4) with a GIF
   fallback? A 60-second full-motion GIF under 2.5 MB is a tight budget and
   the weight is likely to be paid in frame rate or colours. A webm holds
   the same tour at a fraction of the size, plays inline on the Pages site
   and in the README on GitHub, but is not a still image in every context a
   GIF is.
2. **Speed.** Faster because the *capture* is tighter (no dead air, no
   hunting, fewer redundant scrolls), or faster because the footage is
   sped up in post? The first is honest about how the tool feels to use;
   the second fits more in but shows a panel nobody's hands could drive.
   My preference is the first, with post-speed only over genuinely dull
   spans such as an index rebuild.
3. **The story.** Proposed: *"I want lazygit, I don't know if it's in
   nixpkgs, and I don't want to edit a file."* Search from the keybind,
   find it, queue it, see it waiting in Selection, glance at Drafts and
   Options for what else is managed here, Flakes for where else packages
   come from, then apply -- ending on the tool's actual claim, that
   nothing happened until you said so. Is that the story you want told, or
   is the flake input the more interesting hook?
4. **Scope of the re-cut machinery.** Does this task commit a capture
   script (`tools/` or `share/`), or only a documented keystroke list in
   the spec? A script that drives a compositor is itself a thing to
   maintain, and it would be the first such file in this repository.
